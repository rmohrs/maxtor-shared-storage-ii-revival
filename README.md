# Maxtor Shared Storage II – Revival Guide

Bring an old **Maxtor Shared Storage II** NAS back to life: check the disks, rebuild the RAID 1 mirror, repair the firmware's file systems, get permanent SSH access and use it as a backup target for Linux / Proxmox VE.

*Deutsche Kurzfassung: [README.de.md](README.de.md)*

These boxes were expensive back in 2006/2007 and are still perfectly usable as a small, low-power backup drive. Seagate stopped supporting them long ago and most of the knowledge on the web is gone. This repository collects what we learned while reviving one in 2026.

> ⚠️ **Use at your own risk.** You will work as `root` on a box with a 20-year-old kernel. One wrong `dd` or `fdisk` command can wipe your data. Read every guide completely before you type anything, and back up what you cannot lose.
>
> This project is not affiliated with Maxtor or Seagate.

## What you need

- A Maxtor Shared Storage II (2-disk model, e.g. S01R500 / N01R010)
- Shell access to the box (telnet or SSH, usually via a community-patched firmware – see [docs/01-shell-access.md](docs/01-shell-access.md))
- A replacement SATA disk **at least as large** as the old one (exact same size is easiest)
- A computer on the same network (Linux, macOS or Windows with an SSH client)

## The box at a glance

| Item | Value |
|---|---|
| Tested firmware | **3.1.28** (last Shared Storage II release) + community SSH patch |
| CPU | ARM926EJ-S (Marvell 88F5181, `MV-88fxx81`), ~200 MHz |
| RAM | 64 MB (≈ 60 MB usable) |
| Disks | 2 × 3.5" SATA |
| Userland | BusyBox v1.01, `mdadm`, `fdisk`, `e2fsck 1.38`, `smartctl 5.1` (**no** `sfdisk`) |
| File system | ext3 |
| SMB | Samba with **SMB1 only** (no SMB2/3, no NTLMSSP) |
| Data share root | `/share` (RAID 1 device `/dev/md0`) |
| Samba config | `/usr/lib/smb.conf` (generated by the firmware) |

### Disk layout (per disk, 500 GB model)

| Partition | Size | Use |
|---|---|---|
| `sdX1` | ~243 MB | Root file system (`root=/dev/sda1`) |
| `sdX2` | ~243 MB | Firmware configuration / system copy, mounted at `/mnt/__mxo_sda2` |
| `sdX3` | ~243 MB | Swap |
| `sdX4` | rest | Extended partition |
| `sdX5` | ~480 MB | `/tmp` |
| `sdX6` | rest | Linux RAID (type `fd`) → member of `/dev/md0` → `/share` |

**Important:** only partition 6 is mirrored by the RAID. The operating system lives on the first disk (`sda1`, `sda2`, `sda5`) only – unless you copy it yourself ([docs/04-mirror-system.md](docs/04-mirror-system.md)).

## Lessons learned (TL;DR)

- **Used replacement disks lie.** A second-hand disk that looks fine can throw *medium errors* during the first full resync. Run a SMART long test first – `smartctl` is on the box.
- **The firmware rewrites `/etc` on every boot.** A root password you set with `passwd` is gone after a reboot. Use an SSH key in `/root/.ssh` instead – `/root` survives.
- **Run `e2fsck` once.** After years in a cupboard the ext3 file systems had never been checked; the config partition had a corrupted directory.
- **SMB1 only.** Modern clients need `vers=1.0` and `sec=ntlmv2`. Plain file copies work fine, but heavy workloads (e.g. Proxmox Backup Server's chunk store) crash `smbd`. Use simple `vzdump` archives instead.
- **No Finder access on current macOS.** The box does not even announce itself as a file server via Bonjour, and current macOS cannot connect via SMB1 anyway. Use Linux as the client or copy over SSH.
- **Clients must not hang when the box is off.** Mount with `soft` and systemd automount, otherwise a powered-off Maxtor can freeze processes on your server.
- **Realistic speed:** ~75 MB/s RAID resync, ~10 MB/s writing over SMB1.
